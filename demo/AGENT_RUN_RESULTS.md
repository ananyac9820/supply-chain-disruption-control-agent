# Ten chaos events through the agent node path

Generated by `demo/agent_hidden_tests.py`. Each event gets a fresh database, a
fresh sandbox reseed, a reset agent clock, a fresh tool ledger and its own
checkpointer thread, then runs the full graph: monitor → impact → investigate
→ plan → gate → execute, with the tool ledger, verification and escalation
gate in the loop. The escalation is resumed with `approve`.

Reference is Person A's deterministic table in `HIDDEN_TEST_RESULTS.md`, which
drives sandbox → solver → guardrails directly with no nodes.

**Caveat on what "full agent" means here.** No `ANTHROPIC_API_KEY` resolves in
this environment, so every run used `RuleBasedLLM`, the deterministic stand-in
Person B built behind the same protocol. The node path, tool ledger, cache,
verification, guardrail loop and escalation gate are all genuinely exercised.
**LLM tool selection and triage are not.** A run with a live credential could
select a different tool order, and that is exactly the axis this table cannot
speak to.

## Finding 1 — H-10 fires G5 as well as G12, and the agent is the one that is right

The deterministic harness passes `validate()` only `approval_limit` and
`remaining_budget`. G5 is designed not to fire when its inputs are absent, so
the harness **cannot** report a safety-stock breach: it never supplies
`projected_stock` or `safety_stock`. The agent passes the fuller context and
G5 fires with a real reason:

> plan leaves projected stock at -1010 against a safety floor of 150
> (1160 short) with no justification recorded

That is correct. H-10 flips PROD-914 to high priority with `max_delay_days` 0,
both orders become undelayable, and no plan can hold the safety floor.

**This is a defect in `demo/hidden_tests.py`, not in the agent.** The harness
under-reports guardrails on every row, and it happens to be visible only on
H-10 because that is the only case where the extra rule has anything to say.
Not fixed here, per instruction. When it is fixed, the H-10 reference row
becomes `G12, G5` and the other nine rows should be re-checked rather than
assumed unchanged.

## Finding 2 — H-10 reports a different binding constraint, and the candidate set is why

| | binding constraint | eligible suppliers reaching the solver |
|---|---|---|
| deterministic harness | `deadline` | 4 |
| agent node path | `available_quantity` | **1** |

Both are internally consistent. With four suppliers, capacity is 1,450 against
1,160 of demand, so quantity is not what binds and relaxing the deadline
restores feasibility — `deadline`. With one supplier there is not enough
material in the world at all, so quantity binds first.

The agent's own audit trail is explicit about the collapse:

```
[calculation] 4 of 5 suppliers pass certification and the quality floor
[calculation] 3 quotes returned, valid 6h
[calculation] solver input assembled: 1 eligible suppliers, 2 orders
```

Four pass the filters, three are quoted, one reaches the solver. Every other
event assembles 4 (H-03 assembles 3, correctly, because it drops one below the
quality floor). H-10 is the only row where the count collapses, and the only
event that changes a *production order* rather than a supplier or the
inventory.

**Why is not established.** The candidate set is built in
`agent/solver_input.py`, which nets open-PO commitments out of both demand and
supplier availability — a model of in-transit units that the Track A builder
does not have at all. `apply_commitments()` selects commitments per order
against `deadline_day + max_delay_days`, and H-10 sets `max_delay_days` to 0
on the order that previously had 5. That is the obvious place to look and it
is Person B's module, so the diagnosis belongs to them rather than to a guess
recorded here as fact.

**Why it matters beyond one row.** `binding_constraint` is what the escalation
brief tells a human when nothing can be done. "We cannot get enough material"
and "we cannot get it in time" call for different responses from an ops
manager — chase alternative supply versus renegotiate a deadline. If the
candidate set is wrong, the brief names the wrong lever, and the plan is
INFEASIBLE either way so nothing downstream catches it.

## Not a finding: the tool budget

Runs charge more calls than `TOOL_BUDGET_PER_DISRUPTION` (15) without G10
firing, which looks wrong until you read `ledger.check_budget`: the cap
governs **investigation**, not execution. H-01 makes 29 tool calls, 5 served
from cache and logged as avoided, 13 charged against investigation, leaving
2 of 15. ERP writes in the execute phase are deliberately not charged, on the
grounds that a plan that cannot write itself back is a worse failure than the
one the budget exists to prevent. Working as designed.
